# 오다가다 v2.2 — 타일 기반 POI 로딩(격자 캐시·누적) 설계

- 작성일: 2026-07-19
- 상태: 브레인스토밍 승인 → 구현 계획으로
- 상위: v2.0c 브라우즈 모드(뷰포트 검색)의 데이터 선정 방식 재설계
- 저장소: `~/dev/odagada`

## 1. 문제 / 목표

### 1.1 현재 동작과 문제
브라우즈 모드는 카메라가 정지하면 **"현재 중심에서 가까운 20개"**(Nearby Search, DISTANCE, maxResultCount 20)를 검색해 핀으로 표시한다. 지도를 조금만 옮겨도 **중심이 바뀌며 어느 20개가 뽑히는지 자체가 재추첨**된다. 그래서:
- 이전에 21번째였던 POI가 중심 이동으로 top-20에 들어와 **"없던 핀이 튀어나오고"**, 반대로 있던 핀이 사라진다.
- 팬할 때마다 표시 집합이 churn(요동)해 부자연스럽다.

이는 렌더링 지연(오버레이 미끄러짐)이 아니라 **데이터 선정 문제**다. 원인은 **20개 상한 + 중심-앵커 검색**.

### 1.2 자연스러운 지도의 두 성질
- **완전성**: 보이는 영역의 POI를 (거의) 다 보여준다.
- **안정성**: 팬해도 같은 POI가 그대로 유지된다(깜빡·재추첨 없음).

목표: 20개 상한을 우회해 이 두 성질을 확보한다.

### 1.3 API 제약
Google Places **Nearby Search (New)는 호출당 최대 20개, 페이지네이션 없음**(하드 캡). "한 번에 더 많이"는 불가 → **영역을 나눠 여러 번 검색하고 합치는** 구조가 필요하다. (구현 계획 단계에서 정확한 상한·페이지네이션 유무 재확인.)

### 1.4 완료 정의
- 지도를 작은 폭으로 팬해도 핀 집합이 그대로 유지된다(재추첨/깜빡 없음). 새 API 호출도 없다(캐시 히트).
- 새 구역으로 이동하면 그 구역이 **채워지고**, 이전 구역 핀은 사라지지 않고 유지된다(축출 범위 전까지).
- 확대할수록 더 촘촘히 보인다.
- 내/친구 오버레이는 20-상한과 무관하게 항상 표시(기존 동작 유지).

## 2. 아키텍처

지도 데이터를 받는 표준 방식(슬리피 타일)을 따른다. 뷰포트를 **z/x/y 타일**로 나눠 타일 단위로 검색·캐시·렌더한다.

### 2.1 타일 정의 (순수 함수)
- `tileZoom = 카메라 줌 반올림`(clamp). 줌인하면 타일이 작아져 밀도가 오른다 — 20-상한이 더 좁은 영역에 적용되어 "확대할수록 촘촘히"가 자연스럽게 성립한다(고정 미터격자와 달리 확대해도 20에 막히지 않음).
- Web Mercator 슬리피 타일 표준: `tileX = floor((lng+180)/360 * 2^z)`, `tileY`는 표준 머케이터 위도 공식. 각 타일의 경계(bounds) → 중심(center) + 반경(radius = 반대각선 거리).
- `tilesCovering(bounds, z)`: 경계를 덮는 (x,y) 타일 목록.
- 이 계층은 외부 의존 없는 순수 함수로 단위 테스트한다.

### 2.2 검색 가드 (너무 축소된 경우)
- `카메라 줌 ≥ minBrowseZoom`(초기값 14) **그리고** `뷰포트 타일 수 ≤ maxTiles`(초기값 12)일 때만 주변 검색을 수행한다.
- 조건 미달(도시 전체 등)이면 주변 핀 없이 **내/친구 오버레이만** 표시한다(자연스럽고 비용도 방지).

### 2.3 타일 캐시 (`TileCache`)
- `Map<String, List<Poi>>` — 키 `"z/x/y"`. **키가 존재 = 그 타일 검색 완료**(결과가 0개여도 빈 리스트로 저장 → 빈 타일 재검색 방지).
- 축출: 현재 뷰포트에서 먼 타일부터 LRU/거리 기준 축출, 총 타일 상한(초기값 80)으로 메모리·렌더 핀 수 억제.
- 메서드:
  - `missingTiles(List<TileKey> covering)`: 아직 검색 안 된 타일만 반환.
  - `ingest(TileKey, List<Poi>)`: 결과 저장(0개도 저장).
  - `poisIn(bounds)`: 뷰포트에 걸친 타일들의 POI 합집합(id 중복 제거) 반환.
  - `evict(center)`: 상한 초과 시 먼 타일 제거.
- 순수/결정적이라 단위 테스트 가능.

### 2.4 타일 검색원 (`TiledPoiSource`)
`ViewportSearcher`를 대체한다. provider(`GooglePlacesProvider`)와 `TileCache`를 조합:
```
load(bounds, cameraZoom) →
  if !browseAllowed(bounds, cameraZoom): return cache.poisIn(bounds)  // 가드
  z = round(cameraZoom)
  covering = tilesCovering(bounds, z)
  missing = cache.missingTiles(covering)
  await (동시성 캡, 예 4) missing 각각: provider.searchNearby(tile.center, tile.radius) → cache.ingest(tile, result)
  cache.evict(bounds.center)
  return cache.poisIn(bounds)
```
- **작은 팬** = covering이 이미 캐시됨 → missing 없음 → 호출 0, 동일 POI 반환(재추첨 0).
- **새 구역** = 새 타일만 검색해 채움, 기존 타일 유지.
- provider 실패(타일별)는 삼켜서 나머지는 진행(현행 관례).

### 2.5 데이터 흐름 (`map_screen._runSearch`)
1. `TiledPoiSource.load(bounds, zoom)` → ambient POIs(뷰포트 내 누적 합집합).
2. bounds에서 center·radius를 파생(`center = (ne+sw)/2`, `radius = distance(center, ne)`)해 `savedPoisInViewport(center, radius)` + `friendOverlay(..., center)`로 내/친구 오버레이 병합(오버레이 로직 자체는 기존과 동일, 20-상한 무관).
3. dedup 후 `setPins`. 오버레이는 항상 포함.
- stale 가드(`gen`)·friend 실패 무중단 등 기존 로직 유지.

## 3. 인터페이스 변경

- `map_view.dart`의 `onCameraIdle` 콜백: `(LatLng center, double radiusMeters)` → **`(bounds, double zoom)`**. bounds는 코어 `LatLng`의 ne/sw를 담는 간단한 값 객체(`core/models`에 `LatLngBounds{ne, sw}` 신설 — gmap 타입과 분리). `google_map_view._handleCameraIdle`가 `getVisibleRegion()`의 ne/sw와 `_camZoom`을 그대로 전달.
- `map_screen`: `_onCameraIdle`/`_runSearch`가 bounds+zoom을 받아 `TiledPoiSource`에 전달. `_lastCenter`/`_lastRadius` 등 재검색 즉시반영 로직은 bounds 기반으로 조정.
- `google_map_view`의 핀 렌더(`_buildPins`)·오버레이 병합·팔로우·프로그램이동 플래그는 **변경 없음**.
- `ViewportSearcher`는 `TiledPoiSource`로 대체(파일 교체). `RecommendEngine`/`Pipeline`은 계속 핀 소스에서 제외(보존).

## 4. 성능 리스크 (검증 포인트, 이번 범위 밖 대응)

POI가 많아지면(중간 줌에서 40~120개) **커스텀 Flutter 오버레이가 매 프레임(onCameraMove) 재투영하는 위젯 수가 늘어 미끄러짐/잰크가 재등장**할 수 있다. 이는 데이터(타일) 문제와 **별개인 렌더 문제**다.
- 이번 범위: 데이터 계층(타일 캐시·누적)만. 렌더는 오버레이 유지.
- 온디바이스 전후 녹화(동일 기법: `adb screenrecord` + ffmpeg 프레임)로 완전성·안정성·부드러움을 검증한다.
- 잰크가 심하면 **후속 증분**으로 렌더를 네이티브 마커(BitmapDescriptor + markerId diff)로 전환한다. 타일 데이터 계층은 그대로 재사용된다.
- 완화(선택, 계획서에서 결정): 축출 상한(80타일)과 minBrowseZoom로 렌더 핀 수를 실용 범위로 유지.

## 5. 테스트

- **타일 수학**(순수): `tilesCovering`, 타일 center/radius, tileX/Y 변환. 알려진 좌표로 단위 테스트.
- **TileCache**(순수): missingTiles(부분 캐시), ingest(0개 저장), poisIn(합집합·경계 교차·dedup), evict(상한·거리). 단위 테스트.
- **TiledPoiSource** + 페이크 provider: (a) 누락 타일만 호출, (b) 작은 팬 시 호출 0·동일 결과, (c) 빈 타일 재검색 안 함, (d) 가드(축소) 시 검색 안 하고 오버레이만. 단위 테스트.
- **map_screen**: 페이크 TiledPoiSource로 bounds+zoom 배선·오버레이 병합·stale 가드 위젯/단위 테스트.
- **온디바이스**: 전후 녹화 비교 — 작은 팬 시 핀 유지(재추첨 없음), 새 구역 채워짐, 확대 시 촘촘. Supabase 친구 테스트 데이터 유지.

## 6. 파라미터 초기값 (계획서에서 튜닝)
- `minBrowseZoom = 14`
- `maxTiles(뷰포트 검색 허용) = 12`
- `동시 검색 캡 = 4`
- `캐시 타일 상한 = 80`
- `tileZoom = round(cameraZoom)` (필요 시 offset/clamp)
- Nearby: maxResultCount 20, includedTypes 7종, rankPreference DISTANCE (기존 유지)
